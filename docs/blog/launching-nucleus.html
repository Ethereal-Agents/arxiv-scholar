The Expensive Failure Mode Nobody Talks About

AI coding agents across your team share no memory. Every agent starts every task from a blank slate.

A team of five developers uses AI coding agents to work on the same repository. Developer A's agent spends 6.6 million tokens and 135 tool-call steps resolving a Django issue, discovering along the way that a particular AST visitor requires a non-obvious node.col_offset check. Developer B's agent starts a related task the next day—on a different machine, in a different session—and burns tokens making the exact same discovery. Developer C's agent contradicts both, introduces a regression, and Developer D's agent spends thousands of tokens debugging it.

The root cause is structural: each developer's agent operates in isolation. Facts, conventions, gotchas, and architectural decisions discovered by one agent are invisible to every other agent on the team. You pay for the same knowledge repeatedly—in tokens, in latency, and in code quality. Naive approaches like dumping raw execution traces into a shared vector database drown retrieval in noise: agents retrieve a 2,000-line JSON diff when they need a single sentence about an algorithm constraint.

Nucleus eliminates this failure mode. It provides a centralized, shared memory hub that captures structured knowledge from every agent's work and makes it available to every other agent across the team—across machines, across runs, across time—via the Model Context Protocol (MCP).

How Teams Use Nucleus: Diff-Based Fact Extraction at Merge Time

Knowledge enters the hub when feature branches merge to main. Knowledge exits the hub when any agent on any machine calls memory_search.

The integration model is designed around the Git workflow your team already uses. When a developer's agent works on a feature branch, it discovers facts about the codebase—architectural constraints, API behavior, edge cases, gotchas. When that feature branch is merged to main, Nucleus extracts structured facts from the diff and pushes them to the centralized memory hub. From that point forward, any agent on any developer's machine can retrieve those facts via memory_search.

This design means the hub accumulates institutional knowledge organically. Every merged PR enriches the shared memory. A new developer joining the team on day one gets the benefit of every fact every agent has ever discovered, without reading a single internal wiki page. Their agent queries Nucleus and receives precisely scoped, gotcha-prioritized context before writing a single line of code.

The Agent Lifecycle: Four MCP Calls

Any MCP-compatible agent (Claude Code, Cursor, Windsurf, Cline, or a custom client) connects to the Nucleus server and follows a four-call lifecycle. The tool descriptions, including fact extraction instructions, are embedded directly in the MCP tool schema and injected into the agent's context automatically by the MCP client. No custom system prompt modifications are required.

agent_lifecycle.py python 
from fastmcp import Client

async with Client("http://your-nucleus-server:8000/sse") as client:
    # 1. Begin — register this agent session
    run = await client.call_tool("memory_begin_run", {
        "agent_id": "dev-alice-agent",
        "repo": "my-org/my-repo",
    })
    run_id = run.data["run_id"]

    # 2. Search — retrieve what prior agents already learned
    context = await client.call_tool("memory_search", {
        "query": "How does the auth module validate tokens?",
        "run_id": run_id,
        "scope": "my-org/my-repo/src/auth",
    })
    # context.content[0].text contains gotcha-prioritized facts from
    # every agent across the team that ever touched src/auth

    # 3. Write — record a new discovery for future agents
    await client.call_tool("memory_write", {
        "content": "The auth module uses RS256 JWTs signed with "
                   "keys from /etc/secrets/jwt-private.pem. "
                   "HS256 is NOT supported — attempting it causes "
                   "a silent 401 with no error message in logs.",
        "scope": "my-org/my-repo/src/auth",
        "run_id": run_id,
        "fact_type": "gotcha",
    })

    # 4. End — finalize session, extract facts from summary
    await client.call_tool("memory_end_run", {
        "run_id": run_id,
        "summary": "[]",  # or JSON array of extracted facts
    })
ℹ️ Feature-to-Benefit: Why Merge-Time Extraction Matters

Extracting facts from diffs at merge time (rather than during live agent sessions) ensures that only validated, code-reviewed knowledge enters the hub. Draft branches, abandoned experiments, and reverted changes never pollute the shared memory. The hub reflects the merged truth of your codebase, not the noise of work-in-progress.

Architecture: Two Pipelines, One SQLite File

Nucleus operates around two core data pipelines—the Write Path and the Read Path—backed by a single SQLite database running in WAL mode.

The Write Path: From Raw Insight to Deduplicated Fact

When an agent calls memory_write or when facts are extracted from a merged diff via memory_end_run, the incoming content passes through a six-stage ingestion pipeline. Each stage prevents a specific category of data quality degradation.

01
SHA-256 Dedup
Hash of content|scope. Identical writes short-circuit at 0 ms, 0 tokens.
02
Embed
nomic-embed-text-v1.5 via ONNX. 768-dim vector, L2-normalized.
03
KNN Candidates
sqlite-vec finds top-5 similar valid facts within the same scope.
04
LLM Consolidation
Classifies as INDEPENDENT, DUPLICATE, or CONSOLIDATED.
05
Post-Split
Merged facts > 150 words are split into self-contained chunks.
06
Atomic Commit
Facts, vectors, FTS, and lineage in one SQLite transaction.

Stage 1 catches exact duplicates with zero compute cost—a SHA-256 hash of content|scope is checked against the content_hash column. Stage 4 is the critical differentiator: the ConsolidationEngine invokes an LLM (default: DeepSeek V4 Flash) at temperature=0.0 with structured JSON output. When contradictions exist between old facts and new ones, the engine merges them into a single comprehensive fact, resolving contradictions in favor of the newer information while preserving all non-contradictory technical identifiers—error codes, function names, algorithm names—verbatim. Superseded facts are soft-deleted (valid_to is set), not destroyed, preserving full historical lineage.

The Read Path: From Query to Gotcha-First Context

When an agent calls memory_search, the query passes through a seven-stage retrieval pipeline that combines dense semantic search, sparse keyword matching, temporal decay, and session-aware deduplication.

01
Scope Tiers
repo/src/auth → repo/src → repo. Hierarchical expansion.
02
Dense KNN
sqlite-vec cosine similarity ≥ 0.60 threshold.
03
Sparse BM25
FTS5 trigram tokenizer + stop-word filter & vector distance gate (D_L2 ≤ 0.8944).
04
RRF Fusion
Dense (1.0) + BM25 (0.8) via Reciprocal Rank Fusion, k=60.
05
Confidence Decay
1%/day decay, floor at 50%. Biases toward recency.
06
Gotcha Priority
GOTCHA-typed facts force-ranked to position 1.
07
Session Dedup
Previously surfaced facts excluded per run_id.

The hybrid strategy exists because neither dense nor sparse search alone is sufficient for developer knowledge. Dense embeddings capture semantic meaning (“how does authentication work?”) but miss exact identifiers. BM25 catches exact matches on function names, error codes, and variable names but misses semantic similarity. Importantly, Nucleus applies thresholding to sparse retrieval as well: the query sanitizer strips 32 stop-words and short tokens (≤ 2 characters), while the FTS5 search joins facts_vec to enforce the same semantic distance gate (D_L2 ≤ 0.8944, equivalent to cosine similarity ≥ 0.60). If a query contains only stop words, BM25 gracefully short-circuits to dense-only search. This dual thresholding ensures BM25 acts as a high-precision keyword booster without admitting out-of-context token collisions. Reciprocal Rank Fusion merges both ranked lists using Score(d) = Σ (w / (k + rank(d))) with k=60, normalizing across disparate score distributions and rewarding cross-list agreement.

Gotcha-first re-ranking directly prevents the most expensive category of agent failure. When an agent encountered a non-obvious failure—a silent data corruption, a misleading API response, a version-specific incompatibility—and any developer's agent recorded it as a GOTCHA, every future agent on any machine searching that scope sees that warning first. This turns one agent's 30-minute debugging session into a 0-second lookup for every subsequent agent on the team.

Component Deep Dive

Nucleus is composed of five modules. Each module owns a single responsibility.

⚙️

Core · Configuration & Primitives

Central configuration via environment variables with strict defaults. Defines all Pydantic data models (Fact, Run, SearchResult, WriteResult), five fact type enums (INSIGHT, CONVENTION, ARCHITECTURE, GOTCHA, DEPENDENCY), UUIDv7 time-sortable ID generation, and correlated context logging that tags every log line with run_id via Python contextvars.

🧠

Core · Embedding Model

Wraps nomic-ai/nomic-embed-text-v1.5 (137M parameters) running locally via FastEmbed's ONNX runtime—no GPU required, no external API calls for embeddings. Supports Matryoshka slicing: vectors truncate from 768 to 256 dimensions for 3× storage savings with ~5% quality reduction. Enforces mandatory prefix protocol (search_document: for storage, search_query: for retrieval)—omitting these degrades accuracy by ~15%.

🔀

Ingestion · Consolidation Engine

The semantic deduplication brain. Compares incoming facts against KNN candidates using an LLM at temperature=0.0 with structured JSON output. Classifies each relationship as INDEPENDENT, DUPLICATE, or CONSOLIDATED and merges contradicting facts. When merged text exceeds 150 words, the splitter breaks it into self-contained atomic chunks, resolving all pronoun references and preserving keyword vocabulary for FTS fidelity.

✍️

Ingestion · Fact Writer

Transaction orchestrator for the write path. Executes the full six-stage pipeline: SHA-256 dedup → embedding → KNN candidate search (cosine distance ≤ 0.7071) → LLM consolidation → word-count splitting → atomic SQLite transaction. Writes facts, embeddings, FTS5 entries, and lineage records in a single BEGIN/COMMIT block. Supports explicit supersedes_hint for agent-directed fact replacement.

🔍

Retrieval · Fact Reader

Hybrid search engine executing parallel dense KNN (via sqlite-vec) and sparse BM25 (via FTS5 with trigram tokenization, 32 stop-words removed, and a D_L2 ≤ 0.8944 semantic distance gate) retrieval lanes, merged via Reciprocal Rank Fusion (dense 1.0, BM25 0.8, k=60). Applies bi-temporal confidence decay (1%/day, floored at 50%), forces GOTCHA-typed facts to the top, and filters out previously surfaced facts per run_id. Supports point-in-time time-travel queries via as_of.

🖥️

Server · MCP Interface

FastMCP server exposing six tool endpoints over SSE transport (default port 8000): memory_begin_run, memory_write, memory_search, memory_invalidate, memory_list_runs, and memory_end_run. Includes in-memory session management (2-hour TTL), agent-optimized presentation formatting (strips float scores, prepends ⚠ to gotchas), and docstring-driven fact extraction that embeds instructions directly in MCP tool descriptions—no custom system prompts required.

Bi-Temporal Versioning: Facts Have Two Timelines

Every fact in Nucleus carries two independent time dimensions. valid_from and valid_to model the real-world validity window—the period during which the fact was considered true. created_at models the transaction time—when the fact entered the system. This separation enables point-in-time time-travel queries (pass as_of to memory_search to retrieve the knowledge base as it existed at any timestamp) and non-destructive contradiction resolution (old facts are time-bounded, not deleted, with lineage records linking predecessors to successors).

The Storage Layer: SQLite, Tuned for Concurrency

Nucleus uses a single SQLite database file in WAL mode—a deliberate architectural choice. WAL mode enables concurrent readers alongside a single writer. The database runs with a 64 MB in-memory page cache, 5-second busy timeout, synchronous=NORMAL for fast commits with WAL crash resilience, and foreign keys enforced. Two virtual tables backed by C extensions power search: facts_vec (sqlite-vec vec0 storing 768-dim float32 vectors) and facts_fts (FTS5 with trigram tokenization for BM25).

ℹ️ Why SQLite, Not Postgres or a Managed Vector DB?

Nucleus targets a deployment model where the memory server runs as a centralized service for your team. A single-file database eliminates connection string management, credential rotation, and cold-start delays for serverless vector DB instances. You can copy swarm_memory.db to a new machine and your entire team's knowledge base travels with it. For teams that require PostgreSQL, the storage layer is isolated behind a clean interface in swarm_memory/store/db.py.

Step 3: Write a Fact and Search for It

first_run.py python 
import asyncio
from fastmcp import Client

async def main():
    async with Client("http://localhost:8000/sse") as client:
        # 1. Begin a session — returns a UUIDv7 run_id
        run = await client.call_tool("memory_begin_run", {
            "agent_id": "onboarding-agent",
            "repo": "my-org/my-repo",
        })
        run_id = run.data["run_id"]
        print(f"Run started: {run_id}")

        # 2. Write a fact — passes through the full 6-stage pipeline
        write = await client.call_tool("memory_write", {
            "content": "The auth module uses RS256 JWTs signed with "
                       "keys from /etc/secrets/jwt-private.pem. "
                       "HS256 is NOT supported — attempting it causes "
                       "a silent 401 with no error message in logs.",
            "scope": "my-org/my-repo/src/auth",
            "run_id": run_id,
            "fact_type": "gotcha",
            "confidence": 1.0,
        })
        print(f"Write result: {write.data['message']}")

        # 3. Search — simulating a different developer's agent
        context = await client.call_tool("memory_search", {
            "query": "How does authentication work in this repo?",
            "run_id": run_id,
            "scope": "my-org/my-repo/src/auth",
        })
        print(f"\n--- Retrieved Context ---\n{context.content[0].text}")

        # 4. End the run
        await client.call_tool("memory_end_run", {
            "run_id": run_id,
            "summary": "[]",
        })
        print("\nRun ended successfully.")

asyncio.run(main())

Mental Model: How Facts Flow Through the System

Think of Nucleus as a knowledge ledger for your team's agents, not a cache. Facts are never overwritten in place. When new knowledge contradicts existing knowledge, the old fact is time-bounded (its valid_to is set), a new merged fact is created, and a lineage record links the two. Current queries see only facts where valid_to IS NULL. Time-travel queries filter by the valid_from ≤ as_of window. The database only grows; there are no destructive updates.

Error Handling and Edge Cases

⚠️ LLM Consolidation Failure

If the consolidation LLM returns malformed JSON, times out, or is unreachable, the engine does not crash and does not block the write. It falls back to INDEPENDENT classification and stores the fact as-is. You may accumulate near-duplicates during an LLM outage, but you will never lose data and the write path never throws an unhandled exception.

⚠️ Malformed Agent Extraction Output

The memory_end_run tool accepts a summary parameter containing JSON-formatted extracted facts. Agents frequently produce malformed JSON—trailing commas, missing brackets, markdown-fenced code blocks. The parser handles this with a 4-stage resilient pipeline: strip markdown fences → standard parse → regex repair trailing commas → validate individual items via Pydantic. Valid items are preserved; malformed items are logged and skipped. memory_end_run always succeeds.

⚠️ Embedding Model Cold Start

The ONNX embedding model (137M parameters) is lazy-loaded on first invocation, not at server startup. The first memory_write or memory_search call incurs a one-time loading delay. To eliminate this, send a throwaway search query after server startup.

MCP Tool Endpoints

Six tools compose the complete agent lifecycle. Every tool validates inputs, returns structured responses, and never throws unhandled exceptions to the MCP client.

Tool Purpose Key Parameters
memory_begin_run Registers a new agent session. Returns a UUIDv7 run_id. Validates repo format. repo, agent_id, branch, model
memory_write Ingests a single fact through the 6-stage write pipeline. Validates confidence (0.0–1.0) and content length. content, scope, run_id, fact_type, confidence, supersedes_hint
memory_search Executes the 7-stage hybrid retrieval pipeline. Over-fetches to guarantee top_k fresh results after session deduplication. query, run_id, scope, as_of, top_k, fact_type
memory_invalidate Soft-deletes a fact by setting valid_to. Use when an agent discovers a recorded fact is incorrect. fact_id, reason, run_id, valid_to
memory_list_runs Lists recent runs, including token usage and cost. Useful for observability and cost attribution across developers. run_id, repo, limit
memory_end_run Finalizes session. Parses extracted facts from the summary JSON via the 4-stage resilient parser, writes them, and records token usage. run_id, summary, trajectory, input_tokens, output_tokens, total_cost_usd

Configuration Reference

All configuration is via environment variables. Defaults target a single-machine deployment with an OpenRouter API key.

Variable Default What It Controls
SWARM_MEMORY_DB_PATH swarm_memory.db Path to the SQLite database file.
SWARM_MEMORY_EMBED_DIM 768 Embedding dimensions. Set to 256 for 3× storage savings with ~5% quality reduction (Matryoshka slicing).
SWARM_MEMORY_RRF_K 60 RRF rank-smoothing constant. Higher values dampen top-ranked influence.
SWARM_MEMORY_RETRIEVAL_MIN_SIMILARITY 0.60 Cosine similarity floor for dense retrieval. Converted to L2 distance: √(2 − 2 × 0.60) ≈ 0.894.
SWARM_MEMORY_CONFIDENCE_DECAY_RATE 0.01 Daily score decay rate. A 30-day-old fact scores at max(0.5, 1.0 − 0.30) = 0.70 of its original RRF score.
SWARM_MEMORY_CONFIDENCE_DECAY_FLOOR 0.5 Minimum decay multiplier. Prevents old-but-relevant facts from disappearing entirely.
SWARM_MEMORY_SESSION_TTL 7200 In-memory session dedup TTL in seconds (2 hours).
SWARM_MEMORY_LLM_MODEL openrouter/deepseek/deepseek-v4-flash-0731 LLM for the Consolidation Engine. Supports any LiteLLM-compatible model string.
LOG_LEVEL INFO Logging verbosity. Set to DEBUG to see per-stage pipeline timing.

Prerequisites and Constraints

Nucleus requires Python 3.11 or later, uv for dependency management, and an API key for at least one LiteLLM-supported LLM provider (OpenRouter, OpenAI, or Anthropic). The consolidation engine calls the LLM during writes. Without an API key, writes fall back to INDEPENDENT classification (no deduplication, no contradiction resolution).

The sqlite-vec C extension must load successfully for dense vector search. Pre-built wheels exist for Linux (x86_64, aarch64), macOS (x86_64, Apple Silicon), and Windows (x86_64). On unsupported platforms, Nucleus falls back to BM25-only retrieval. The embedding model runs entirely on CPU via ONNX runtime; no GPU is required.

Nucleus is designed for single-writer deployments. SQLite WAL mode supports concurrent readers but only one writer at a time. If you need multiple concurrent writer processes, place a write queue in front of the MCP server, or run one Nucleus instance per orchestrator.
