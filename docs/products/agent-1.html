Why Build From Scratch?

Existing agent frameworks are powerful but opaque. We needed a controlled testbed.

The landscape of AI coding agents is rich — SWE-Agent, OpenHands, Aider, and dozens of others can resolve real GitHub issues. But they're complex systems: hundreds of heuristics, implicit caching layers, framework-specific context management, custom prompt pipelines. When you add memory on top of one of these agents and see a 30% token reduction, how do you know the improvement came from memory? Maybe a caching layer changed. Maybe the framework updated its retrieval heuristic. The signal drowns in noise.

We faced this exact problem when evaluating Nucleus SwarmMemory. To prove that shared team memory genuinely reduces token waste and improves resolution rates, we needed three things: (1) Absolute control over the context window — knowing exactly what tokens enter and exit the prompt at every step. (2) Reproducible environments — identical Docker containers with deterministic dependency states. (3) Clean tool interfaces — tools that don't secretly inject hidden context or side-channel information.

So we built Agent-1. It's not trying to be the best coding agent. It's trying to be the most measurable one. Every line of code is auditable, every token is tracked, and the only variable between a baseline run and a memory-augmented run is the presence of Nucleus. What follows is a deep dive into every component — how they work, why they're designed the way they are, and what we learned building them.

Think of it like a scientific experiment: Agent-1 is the lab equipment. Nucleus is the treatment. SWE-bench is the test population. We built the equipment from scratch so we could trust the measurement.

The ReAct Loop, Context Compaction & Prompt Caching

Three systems that work together to keep the agent fast and within token budgets.

The ReAct Loop

The core of Agent-1 is a ReAct (Reasoning and Acting) loop. The agent thinks, picks a tool to use, observes the result, and repeats. This Reasoning-Acting cycle continues until the task is solved or the step limit is reached.

  • Loop runs while step_count < max_steps (200)
  • Each iteration: call LLM → parse response → execute tool calls → append results → check if compaction needed
  • Soft-nudge recovery: if the model returns no tool calls, the agent nudges it:
    • Empty response: "Your response was empty and did not contain a tool call. Please use a tool to continue your task, or call finish if you are done."
    • Text-only response: "You must use a tool (such as bash, read_file, edit_file) to interact with the environment, or call finish if you are completely done."
    • After 3 consecutive no-tool responses → hard termination
  • Four termination conditions: (1) finish tool called, (2) 3 consecutive nudges, (3) max 200 steps, (4) LLM returns empty

Sawtooth Context Compaction

LLMs have a maximum input size. When the conversation exceeds this, the agent needs to summarize older messages to make room for new ones — like clearing your desk but keeping the most important notes.

  • Triggered when current_tokens > 75% of max_input_tokens (fallback: 100,000 tokens)
  • Head = first 2 messages (system prompt + original task) — ALWAYS preserved
  • Tail = last 5 messages — ALWAYS preserved (adjusted to avoid splitting tool/assistant pairs)
  • Middle = everything between head and tail — summarized by a secondary model using a dedicated compaction prompt
  • Result: [head] + [middle_summary] + [tail] — the summary is tagged with [SYSTEM MEMORY COMPACTION]
  • Why "Sawtooth": Token count rises linearly with each step, then drops sharply on compaction, then rises again — creating a sawtooth waveform over time

Sliding-Window Prompt Caching

Every time the agent calls the LLM, it sends the entire conversation history. Most of this history hasn't changed since the last call. Prompt caching tells the LLM: 'I'm marking a checkpoint — everything before this point is the same as last time, so reuse your cached computation.' This dramatically cuts latency and cost.

  • When len(messages) ≥ 4, the N−2 message (second-to-last) gets {"cache_control": {"type": "ephemeral"}}
  • Why N−2: The last message changes every step (new tool output), but the second-to-last is stable — natural cache boundary
  • Everything before N−2 gets cached; only the latest exchange is recomputed
  • Tracks: input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, cost
llm_service.py python 
# Sliding-window prompt cache — checkpoint at N-2
if len(messages) >= 4:
    cache_target = messages[-2]
    cache_target["content"] = [{
        "type": "text",
        "text": cache_target["content"],
        "cache_control": {"type": "ephemeral"}
    }]

Precise Instruments, Not Swiss Army Knives

Six tools, each designed for correctness and token efficiency.

ToolDescription
read_file1-indexed line slicing with start_line / end_line
editExact str_replace matching — not sed, not line-numbers
insertInsert new code after a specific line number
code_searchRipgrep wrapper — results grouped by file in XML
bashGuarded command execution with timeout and destructive-command blocking
finishGenerate git diff patch against initial commit and terminate the loop

Why str_replace beats line-number editing: Line-number-based editing (like sed) is fragile. If the agent reads a file at step 5 and edits at step 15, intervening edits may have shifted line numbers. Agent-1's edit tool uses exact string matching — the agent specifies the exact text to find and replace. _count_occurrences() enforces exactly one match. Zero matches or multiple matches return helpful error hints ("whitespace mismatch detected", "first line matches but full block doesn't").

Compile-time syntax checking: After every edit to a .py file, the tool runs compile(content, path, "exec"). If it catches a SyntaxError, the edit is saved but returns a ⚠️ SYNTAX WARNING with the error line — giving the agent immediate feedback to self-correct before running tests.

file_ops.py python 
# Post-edit syntax validation (Python files only)
if path.endswith('.py'):
    try:
        compile(new_content, path, "exec")
    except SyntaxError as e:
        return f"⚠️ SYNTAX WARNING: {e.msg} at line {e.lineno}"

Smart Test Runner: The test runner auto-detects the project's test framework using a simple heuristic (checks for tests/runtests.py → Django, bin/test → SymPy, else → pytest). For pytest, it uses --junitxml to get structured XML output, then parses <testsuite> and <testcase> nodes to extract only failure tracebacks. This is critical — raw pytest console output is verbose and wastes thousands of tokens. The JUnit parser extracts only actionable failure information into a compact <test_run_summary>.

Destructive Command Guard: The bash tool blocks dangerous commands (rm -rf /, chmod 777, etc.) before execution. Commands run with a configurable timeout, and output is returned as structured <stdout>, <stderr>, and <exit_code> XML tags.

Reproducible Sandboxes

How Agent-1 achieves environment reproducibility for fair benchmarking.

DockerEnvironment uses Docker Python SDK to create containers with sleep infinity. Commands execute via docker exec. File transfers use docker cp (NOT volume mounts) — volume mounts cause UID permission conflicts between host and container. docker cp via subprocess.run with a tempdir ensures clean transfers.

Dynamic dependency injection: _ensure_dependencies() detects the container's package manager (apt-get, apk, pacman, yum) and installs ripgrep as root if needed.

get_system_prompt_addition() injects environment-aware instructions into the agent's system prompt:

  • Docker: "You are running inside a Docker container. Standard Linux behavior applies. CRITICAL: You MUST always use absolute paths."
  • Local: macOS-specific warnings

The environment doesn't just run commands — it teaches the agent about itself. By injecting runtime-specific instructions directly into the system prompt, the agent never makes incorrect assumptions about its execution context.

Measure, Grade, Learn

A parallel evaluation harness and a trajectory viewer that became our primary feedback loop.

Parallel Evaluation Pipeline

Two-phase architecture: Inference (run agents) → Grading (verify patches). Inference uses ProcessPoolExecutor for parallel SWE-bench instances, each in its own Docker container.

Container lifecycle: pull pre-built SWE-bench image → create container → copy repo state → run agent → extract patch → destroy container. Grading calls official SWE-bench grader container.

SWE-bench infrastructure fixes we had to make:

  • PEP-517 pinning: older repos break under modern build isolation
  • Django log parser: handles duplicate test name keys
  • Python 3.12 grading fallback: raw log parser for edge cases
  • Git history sanitization: strips ticket refs from commit messages to prevent information leakage

Trajectory Viewer

Streamlit app that parses trajectory.jsonl files. Uses regex to extract <thought> / <thinking> blocks into collapsible "💭 Thinking Process" expanders. One-click "Generate AI Run Summary" streams an LLM-generated post-mortem. These post-mortems were the primary mechanism for refining system prompts and tool designs.

The Trajectory Viewer isn't just a debugging tool — it's Agent-1's primary feedback loop. Every major improvement to the system prompts and tool designs came from reading trajectory post-mortems and asking: where did the agent waste tokens?

The Dual-Agent Cluster Workflow

How Agent-1 integrates with Nucleus SwarmMemory — the controlled variable in our experiment.

This section focuses on how the agent uses memory, not how memory works internally. For the architecture of Nucleus itself — bi-temporal versioning, hybrid retrieval, SQLite internals — see the Nucleus deep dive.

Memory Hub & Strategy

Two strategies:

  • baseline: No memory. Agent starts cold every time. Used for fair baseline measurement.
  • memory: Full MCP integration. Agent reads facts at start, writes facts during execution.

Lifecycle:

  1. begin_run() → calls memory_begin_run on Nucleus MCP server → receives run_id
  2. During execution → agent uses memory_write to record facts with content, fact_type (insight/gotcha/convention/architecture), confidence, scope
  3. end_run() → calls memory_end_run with run_id, token counts, cost

Memory Tools

  • team_memory_search: queries Nucleus for relevant historical facts from previous runs
  • memory_write: records structural findings — fields: content, fact_type, confidence, scope, supersedes_hint

The Dual-Agent Cluster Workflow

For each task in a cluster:

  1. Diff Researcher (50 steps) — runs git diff between commits, traces caller/callee chains, writes facts to Nucleus. Motto: "WRITE EARLY, WRITE OFTEN"
  2. Container Reset — environment reset to clean state
  3. Execution Agent (up to 200 steps) — retrieves facts from Nucleus via team_memory_search and solves the issue. It does not write facts back — the execution agent's patches may contain incorrect assumptions, so we only persist knowledge from the Diff Researcher's controlled analysis.

Special case — first task with --initial-sweep: Initial Sweep Agent (150 steps) does broad structural exploration.

The Numbers

Base agent capability on SWE-bench Verified, and memory's impact across four evaluation clusters.

Base Agent Capability

We ran Agent-1 against 99 instances from SWE-bench Verified using MiMo v2.5 Pro. The automated grader reported a 55.6% pass rate. But automated graders aren't perfect — they can miss correct patches (false negatives) and accept flawed ones (false positives). We analyzed every trajectory and log file to get accurate numbers.

The 10 false negatives fell into three categories: missing testbed dependencies (4 Sphinx tasks needing the roman package), strict warning filters treating third-party deprecation warnings as test failures (4 tasks in Astropy/Matplotlib), and harness parsing bugs (2 tasks where the grader checked for nonexistent test names or couldn't parse tox output).

We report 62.6% rather than the raw 55.6%. The 10 false negatives were caused by evaluation infrastructure issues — not by incorrect patches. We verified each manually by analyzing trajectories, log files, and grader output.

Try It Yourself

Get Agent-1 running in under five minutes.

Step 1 — Install:

Terminal bash 
git clone https://github.com/Ethereal-Agents/agent-1.git
cd agent-1
uv pip install -e ".[eval,viewer]"
cp .env.example .env
# Edit .env → add your OPENROUTER_API_KEY

Step 2 — Run on a local issue:

Terminal bash 
python main.py "Fix the bug described in issue #123" \
  --dir /path/to/repo \
  --memory-strategy baseline

Step 3 — Run with memory:

Terminal bash 
# Start Nucleus MCP server (in a separate terminal)
cd /path/to/Nucleus
uv run python -m swarm_memory.server.mcp_server

# Run with memory enabled
python main.py "Fix the bug..." \
  --dir /path/to/repo \
  --memory-strategy memory

Step 4 — Evaluate on SWE-bench:

Terminal bash 
# 10-instance development tier
python -m eval.run_eval --tier 10 --run-id my-first-run

# View trajectories
streamlit run trajectory_viewer/app.py

✓ If you can run python main.py --help without errors, you're ready to go.
