Team-SWE creates structured task clusters where every coding problem shares deep, verifiable context overlap with all tasks preceding it. Designed specifically for software engineering workloads, it provides the first rigorous benchmark for measuring how well AI agents and agentic memory systems retain, retrieve, and reuse codebase knowledge across sequential tasks—contrasting broad file-level associations with precise AST-level code overlap.

The Core Challenge: Measuring Agent Memory in Code

Isolated benchmarks evaluate zero-shot reasoning. Measuring agent memory requires sequential workloads with guaranteed context reuse.

AI coding assistants are increasingly integrated with memory hubs, vector caches, and bi-temporal knowledge stores. The goal is straightforward: when an agent investigates a codebase module, discovers architectural conventions, or fixes a bug, that accumulated knowledge should directly accelerate subsequent tasks on the same subsystem.

However, measuring whether an agent actually uses its stored memory has been fundamentally limited by benchmark design. Standard coding benchmarks evaluate problems in complete isolation—resetting the agent after every task. If tasks are independent, retrieved memory is either irrelevant or nonexistent, leaving no way to determine whether a memory system compounds engineering productivity or simply adds overhead.

⚡ The Longitudinal Measurement Gap

In real software engineering, developers don't work on disconnected islands of code. They work in continuous streams within the same subsystems. An engineer resolving an expression evaluation bug today carries deep mental context into tomorrow's query compiler task. To test whether an agent can replicate this human compounding, the benchmark must provide time-ordered task sequences where prior context is guaranteed to be relevant.

Team-SWE was built to provide this exact measurement instrument. By automatically constructing task chains with high cumulative structural overlap, Team-SWE ensures that every step in a sequence offers genuine opportunities for knowledge transfer. If an agent's memory system is effective, tokens and costs should decrease across the chain. If it isn't, the benchmark exposes it immediately.

Cumulative Overlap: The Core Metric

The key constraint is cumulative overlap: each task in a cluster isn't just compared to the task immediately before it. Instead, its fingerprint (the set of files or functions it touches) is checked against the union of all preceding tasks' fingerprints.

This means by Task 3 or Task 4, the agent has accumulated rich context from prior tasks, and the cluster's structure guarantees that this accumulated context is relevant to the current task. A task with 0% overlap against the cumulative set breaks the chain—it's excluded.

✓ Why This Matters for Memory Evaluation

If an agent with memory solves Task 1 and stores facts about the modified code, those facts are guaranteed to be relevant when it encounters Task 2, 3, and beyond. The question becomes: does the agent retrieve and reuse that context, or does it rediscover everything from scratch? The cumulative overlap ensures we're measuring memory utilization, not random noise.

🔍 The 500 → 16 Funnel: Why Clusters Are Rare in SWE-bench Verified

SWE-bench Verified contains 500 human-validated tasks across 12 major Python repositories. However, applying these realistic longitudinal constraints (exact version match, ≥1-day chronological spacing, ≤122-day window, ≥3 tasks per chain, and strict cumulative overlap with zero tolerance for disconnected tasks) acts as a severe filter: only 4 clusters totaling 16 tasks survived across the entire corpus.

This scarcity demonstrates why automated cluster mining is essential: naturally occurring, chronologically sequential, subsystem-coherent tasks are needles in a haystack. Team-SWE isolates these rare gems so multi-agent memory researchers can run clean, unconfounded longitudinal experiments.

Two Levels of Overlap Detection

File-based overlap gives broad signal. AST-based overlap guarantees actual code-level context sharing.

Broad Signal

File-Based Overlap

Extracts the set of .py file paths modified by each task's patch. Two tasks overlap if they modify the same files.

  • ✓ Fast — no repo clone needed
  • ✓ Catches all co-located changes
  • △ Same file ≠ same code region
  • △ A file with 50 functions may have unrelated changes
Precise Signal

AST-Based Overlap

Parses patches to extract fully-qualified function and method signatures. Two tasks overlap only if they modify the same functions or methods.

  • ✓ Guarantees actual code overlap
  • ✓ Function-level precision
  • ✓ Strongest signal for memory reuse
  • △ Requires repo clone + checkout
💡 Why Both Matter

File-based overlap is useful for quick discovery—it casts a wide net and runs without cloning repositories. But sharing a file doesn't guarantee sharing context. A single Django model file might contain dozens of unrelated classes and methods. AST-based overlap narrows this to the function level: if two tasks both modify django.db.models.sql.Query.resolve_lookup_value, there's a direct context link an agent's memory can exploit. The shipped clusters use both signals to ensure quality.

How AST Fingerprinting Works

For each task, the pipeline clones the target repository at the task's base_commit, parses the patch to identify modified line ranges per file, then walks the Python AST with a custom FullyQualifiedNameVisitor to determine which function or method each modified line belongs to. The result is a set of fully-qualified identifiers like:

AST fingerprint example json 
{
  "instance_id": "django__django-11049",
  "fingerprint": [
    ["django/db/models/expressions.py", "Combinable._combine"],
    ["django/db/models/expressions.py", "Value.resolve_expression"],
    ["django/db/models/sql/compiler.py", "SQLCompiler.as_sql"]
  ]
}

When Task 2 also modifies Combinable._combine or Value.resolve_expression, the overlap is structural and precise—not just "same file." An agent that previously analyzed these functions has directly reusable context.

Cluster 1: Django AST Eval

AST-Based Overlap 4 tasks · 111 days · 47.5% AST overlap

Mined via the AST overlap pipeline. Four tasks targeting Django's ORM expression evaluation functions in django/db/models/expressions.py, compiler.py, and related query modules. Tasks directly overlap at the function level on Combinable._combine, Value.resolve_expression, and SQLCompiler.as_sql. An agent that resolves Task 1 accumulates internal knowledge of Django's expression tree compilation that is directly reusable for Tasks 2–4.

Cluster 2: Sphinx Domains

100% File Overlap + AST Property Overlap 3 tasks · 49 days · 100% overlap

Three tasks in Sphinx with 100% file overlap and deep AST-level function overlap. Every task modifies Sphinx's Python domain property documenter and annotation subsystem in sphinx/domains/python.py and sphinx/ext/autodoc/. The tasks specifically share AST routines for handling property signatures (PyProperty.handle_signature, PyProperty.get_signature_prefix) and literal type annotations (_parse_annotation, unparse). This high structural coherence explains why Nucleus-equipped agents went from 1/3 to 3/3 resolved on this cluster.

Cluster 3: Django 3.0

File-Based Subsystem Overlap 4 tasks · 71 days · 83.3% overlap

Four tasks in Django 3.0 targeting SQL query compilation, CheckConstraint SQL generation with OR/AND clauses, and FilteredRelation excludes. Tasks share common code paths through django.db.models.sql.query and django.db.backends with 83.3% mean cumulative file overlap.

Cluster 4: Django DB Models

File-Based Subsystem Overlap 5 tasks · 57 days · 75.0% overlap

The longest chain with five tasks over 57 days, covering model save routines, queryset evaluation, and field validation in Django's core db.models subsystem. The 75% overlap threshold guarantees that three-quarters of each task's touched files were explored in previous tasks within the chain.

Key Benchmark Findings

1. AST Overlap Delivers the Steepest Efficiency Gains: On the django__ast_eval cluster (pure function-level AST overlap), memory reduced total token consumption by 55.8% and cost by 62.3%. Because the agent inherited precise knowledge of Combinable._combine and Value.resolve_expression from Task 1, it bypassed exploratory codebase search on Tasks 2–4.

2. Context Overlap Unlocks Solvability: On the sphinx__domains cluster (100% file overlap and AST property parser overlap), the baseline agent failed 2 of the 3 tasks due to context window saturation during search. With memory, the agent recalled the property documenter architecture, solving all 3 tasks (1/3 → 3/3) while cutting cost by 45.4%.

Future Scope: Expanding AST-Based Overlap Clusters

Our immediate research priority is significantly increasing the number and variety of AST-level overlap clusters.

While file-based overlap provides a solid baseline for general subsystem evaluation, AST-based overlap provides the purest ground-truth signal for measuring agent memory utilization. When two tasks modify the exact same functions and AST subtrees, memory systems are directly tested on their ability to retrieve and apply granular, function-specific insights.

🌲

Scaling AST-Level Mining

Expand AST fingerprinting across more open-source repositories and larger multi-repo task corpora to discover 50+ high-coherence AST clusters with function- and method-level overlap.

🔗

Call Graph & Dependency Overlap

Extend AST parsing to incorporate static call-graph and type-hierarchy analysis, identifying tasks that touch caller/callee pairs across file boundaries even when direct edits don't overlap.

🧪

Cross-Language Support

Bring AST overlap extraction via Tree-sitter to JavaScript/TypeScript, Go, and Rust repos to benchmark multi-agent memory in polyglot codebases.
